## Recommended delivery — preserve the existing runtime image

Use one purpose-specific **delivery bundle** secret, proposed name signmons-staging-controlled-intake-material, whose payload is the exact private JSON map expected by startup. Distinct source keys remain separately versioned resources: proposed customer-session-key, customer-digest-key and customer-email-fingerprint-key under signmons-staging prefix; correct existing Twilio token version is an input only after requalification. Names are proposals: collision/purpose checks and explicit provisioning approval come first. No number is guessed.

An authorized local operator tool fetches each approved numeric source version into memory, validates exact shapes/key separation, creates the map and uploads it directly through an authenticated API request. Never payloads in argv, shell substitution, release YAML, stdout, repository, clipboard or an unencrypted file. No customer address or OTP belongs in it. A sanitized provenance receipt binds source numeric resource names, bundle numeric version, source/tool revision and packet ID, without values or low-entropy secret hashes. Private readback comparison must establish equality; labels alone are not proof. JS strings cannot be guaranteed zeroized; short-lived process exit and no dumps/logs are required, not a claim of complete memory erasure.

Cloud Run mapping interface: CONTROLLED_INTAKE_SECRETS_JSON references that bundle's explicit numeric version via secretKeyRef, not an inline value. The runtime receives the map without an application loader change. Runtime accessor scope is the named delivery bundle plus already-reviewed inherited resources; the preparing operator separately needs only approved source-read/bundle-write rights. No project-wide accessor grant inferred. Bundle duplicates sensitive material: audit/rotation must track source and bundle together, and revoke DB approval before retirement. Disabling the secret alone does not invalidate bytes already loaded by running instances.

Google documents startup-time secret environment resolution and recommends pinning versions: https://docs.cloud.google.com/run/docs/configuring/services/secrets (reviewed2026-09-15). This establishes platform capability, not current IAM/resource availability. Alternative: change startup to fetch each numeric resource through ADC; avoids a bundle copy but adds runtime network/client failure handling and a new image/retest. Not recommended for this capped pilot. Manual copying/editing of private JSON is not recommended.

## Runtime/release lifecycle and exact approval operation

Preserve current normal traffic and all unrelated tags. Use existing service signmons-calldesk-staging/us-east5 and runtime identity signmons-calldesk-runtime@signmons.iam.gserviceaccount.com. R09 first qualifies a **disabled** revision with no new intake material. Its revision is not the future enabled revision: changing env creates another revision. R10 must prebind a unique enabled revision suffix/full name and stable approved HTTPS tag origin; R11 verifies actual revision/digest/env references before any participant request. If name/origin differs, stop. Never weaken exact revision matching to reuse a disabled packet.

Freeze exact serialized enabled envelope and both computed digests once. Bind current approved tenant, category, organization/payment snapshots, address account and budgets; no fixture identities. The runtime parser refuses startup before validFrom and after validUntil, so begin the explicitly approved15minute window before enabled deployment/startup. Deployment time consumes the window. Failed/late startup must revoke approvals and stop, not extend times/re-hash/retry automatically. No additional readiness delay hidden outside the cap.

Proposed operator interface (NOT implemented): prepare(packet, privateInputs) returns a sanitized manifest and private bundle upload; activate(packet, expectedTenantUpdatedAt, expectedApprovalState, ownerAuthorization) and revoke(packet, expectedDigests) use the exact isolated child connection. Neither operation changes tenant status or approves organization/payment settings implicitly. If tenant/policy prerequisite is inactive, refuse and enumerate its separately reviewed R07/R08 resource diff.

Activation transaction: verify fixed endpoint/database/role and current26-file migration history; lock exact tenant row FOR UPDATE, check expected updatedAt/settings approvals and DB time/current policy; preserve unrelated JSON; set only controlledRuntimeApproval and controlledPhoneApproval with their respective digests/enabled=true; strictly advance updatedAt and add sanitized audit in same transaction. Row count must equal1. Audit failure or competing mutation rolls back. No unsafe whole-settings replacement or automatic upsert of tenant. An unknown commit result requires read-only reconciliation, not another activation. Release approval and run spending approval remain distinct.

Revocation transaction: same target/tenant lock and exact expected digests; set both enabled=false, preserve digest/other settings and audit atomically. Foreign/newer digest refuses rather than disabling a newer run. Runtime FOR SHARE checks serialize against this write; requests already past a committed reservation may finish and cannot be recalled. Revoke first, then existing session close/purge and disabled release/readback under R12 authority; retain jobs/audits/unknown holds. Expiry is a backstop, not a substitute for verified revocation. Owner explicitly authorizes cleanup at run approval so failure does not prevent shutdown.
