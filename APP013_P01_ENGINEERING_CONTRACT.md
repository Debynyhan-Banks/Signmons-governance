## Trusted service and policy interface — P02

Proposed source: controlled-intake-authority.ts/.spec.ts, consumed by the controlled composition only. The factory receives validated server activation configuration; it returns an opaque capability recognized only by the same process-owned authority object (private identity registry, not a string role or structurally trusted JSON). Every use still rechecks current activation. Never accept that capability from DTO, HTTP header, AsyncLocalStorage user role or serialized queue payload. Never impersonate an operator or remove operator() guards.

Exact activation configuration contract v1: version=1, enabled boolean, tenantId UUID, integrationId nonempty internal label, origin exact HTTPS origin, policyVersion nonempty immutable identifier, organizationApprovedAt ISO instant, organizationDigest SHA256, paymentApprovedAt ISO instant, paymentDigest SHA256, allowedServiceCategoryIds nonempty unique UUID list, priorityPolicy=AUTO_INTAKE_STANDARD_V1, validFrom/validUntil ISO instants, and packetId UUID. Reject missing/extra/invalid fields, indefinite validity, origin path/query/userinfo, unknown priority policy and duplicate category IDs. Compare current tenant/organization/payment/category state inside the transaction, not just at startup. Configuration is injected server-side into composition; no browser write endpoint, new policy editor, IAM resource or database table. Default absent/disabled means no authority. P06 supplies actual reviewed values and immutable config/release binding; example values do not activate anything.

The same-origin customer adapter validates existing session credentials/host/origin/body bounds and binds the request to that activation's tenant/integration. Session capability is customer intent authority only. Separate Firebase operator guards remain for exception/receipt access. Managed-ingress/pre-parser design in the existing card applies; do not broaden CORS or alter webhook raw-body handling. Configuration expiry/revocation must be effective per request and again before commit; no positive authorization cache.

## Submit and transient evidence — P03

Controlled submit port is separate from existing review-only port. Reuse strict sessionToken, requestId, expectedRevision, validated seven-field draft and confirmed=true input; forbid client proof, role, tenant, urgency and policy fields. Immutable submission binding covers session/tenant/conversation, request ID, transcript revision/digest, customer-confirmed draft and active organization/payment/policy versions. Hash only these customer/internal inputs, never Google output. Preserve legacy PENDING_REVIEW contracts; add a distinct controlled result union rather than accepting ADMITTED on the old port.

Sequence:
1. Authenticate session and activation. Under existing lock order, load trusted draft/history and current organization/payment state; refuse cross-tenant, closed, mismatched or stale input. Check existing exact committed receipt first so successful retries cause no provider request.
2. For new admission, verify current phone CHECK evidence from the existing encrypted durable-verification ledger, with source/account/phone-revision/session/policy and expiry binding. Do not promote a closed phone-only test or fixture proof. Add a transaction-scoped controlled reader; reuse freshness arithmetic without retaining FIXTURE_ONLY provenance or weakening fixture mode. Any invalidation remains sticky after edits.
3. Reserve/claim one address operation through existing durable operation/cap accounting, using the trusted submitted draft. Provider I/O occurs outside the job transaction. Do not run the inspection CLI, reuse old holds, or retry automatically. Timeout/unknown dispatch retains liability.
4. Parse with existing Google address and county evaluators. If a correction is needed, return the sanitized allowlisted candidate for explicit confirmation; no job. Confirmation saves customer-confirmed address/revision, not county/verdict. A later explicit submit validates that address again within the existing maximum two-request packet; further corrections preserve progress and stop at the cap. No responseId cache or automatic feedback request.
5. An accepted result for the already confirmed address yields a request-local evidence object containing observed time, operation identity, address revision and evaluator inputs needed for immediate checking. This object never crosses the browser, durable storage, logs, queue or another request. Discard response and evidence on success/error/abort. It is not a restart-proof or across-request cache.
6. Immediately enter the short final transaction, acquire existing locks, and recheck active tenant/session, transcript/draft revisions, organization/payment/activation/category, phone proof, operation ownership and deadline using database time. Address observation must be within the current request's deadline and the unexpired session/activation. The controlled executor uses the existing finite provider deadline; never renew evidence expiry on transaction retry. No provider call while locked. Changed input/policy or missing evidence refuses creation.

LifeSafetyService checks trusted customer-authored turns and current description; earlier unresolved escalation cannot be erased by omission from the latest draft. Missing/invalid history refuses. A match uses existing emergency guidance, not normal job creation. Non-match is not proof of safety; unresolved ambiguity remains an exception. Eligible routine jobs use STANDARD as operational default with unassessed labeling, never humanReviewed=true or OPERATOR_OVERRIDE. No detector pattern expansion or autonomous diagnosis in this contract.

## Atomic persistence and record allowlist — P04

Factor shared persistence from existing persistAdmission, preserving legacy operator semantics on legacy calls. Controlled actor uses existing SYSTEM_AI audit enum with actorId=signmons-intake-admission-v1 and decision source DETERMINISTIC_POLICY; this denotes the application service, not an LLM safety judgment. Customer submission audit remains CUSTOMER. No fake staff identity. Existing unique tenant/intakeSessionId and conversation linkage enforce one logical job; audit/link/consent binding failures roll back the whole transaction.

Controlled intakeAdmission version=2 allowlist: requestId, submissionDigest, transcriptRevision, customerConfirmedAt, actorId, policyVersion, organizationApprovedAt, organizationDigest, paymentApprovedAt, paymentDigest, priorityPolicy, emailChoice. All IDs/digests originate from internal/customer records; time is server-generated. Existing job columns supply job/status/createdAt and customer/property relations. Store the actual customer-confirmed formattedAddress; googlePlaceId/latitude/longitude stay null in this path, addressComponents empty unless populated from separately customer-supplied data. No new schema beyond the already approved nullable migration.

Forbidden in controlled durable receipt/audit: fixtureOnly, currentProof, county, Google verdict/responseId, Google address/coverage references, derived coverage outcome, addressVerification, realVerificationAccepted, hashes of provider content or a permanent Google-certified claim. Phone ledger keeps its separately governed short-lived proof; it is not copied into the job record. Policy version identifies configuration applied to an action, not a reusable factual certificate. Ordinary job/audit lifecycle follows existing retention rules; this is not a new indefinite-retention policy.

Result ADMITTED exposes only authenticated customer's requestId, jobId, state, jobCreated=true and paymentAuthorized/bookingAuthorized/dispatchAuthorized/deliveryAuthorized=false. No provider identifiers, policies, history or credentials. Correction/exception results set jobCreated=false and use fixed reason categories without echoing raw provider diagnostics. Pending/unknown database outcomes never return success.

## Recovery and replay contract

| Interruption | Required behavior |
| --- | --- |
| Before provider dispatch | Existing reservation/claim ownership determines retry eligibility; do not infer no charge from lack of a response |
| After dispatch, before observed result | Preserve unknown liability; no automatic send/retry, no job |
| After result, before committed job | Result is gone on process loss; preserve customer draft, require explicit fresh validation within remaining allowance; never restore proof from a log |
| Policy/edit/stop wins final lock | Refuse job, discard transient result, retain truthful operation liability; no silent cap refund |
| Job committed, response lost | With still-valid customer session and exact submission binding, read committed job/link receipt only; no revalidation or second job |
| Customer session expired after commit | No new customer authority or broad receipt read. Existing authenticated operator recovery can retrieve minimal receipt under tenant/role checks; it does not admit a new job |
| Same request, changed contents | Refuse; never return another submission's receipt or mutate committed job |

Introduce a narrow authenticated receipt-read mode for the controlled customer path, distinct from operator receiptOnly=true. It permits only exact same-session committed receipt lookup while customer credentials and tenant access remain valid; it bypasses no new-write check. New writes always require the normal session lifecycle lock. Reuse exact prior job relation and immutable submission digest validation; do not re-evaluate historical job success against later policy changes. New submissions always use current policy. Duplicate transactions race through the existing unique key/locks; compare exact receipt after a unique conflict rather than blindly treating it as success.
