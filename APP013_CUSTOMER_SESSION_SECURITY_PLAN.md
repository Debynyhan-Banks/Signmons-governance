# APP-013 Customer Consent Session — Local Security Model

Status: **LOCAL MODEL IMPLEMENTED; PRODUCTION ACTIVATION NOT APPROVED.** On 2026-09-09 the owner answered "yes" to implementing and testing a short-lived server-issued customer-session credential with consent bound to the exact mailbox/prompt, while live keys, collection activation and sending remain disabled.

## Implemented boundary

- Latest owner-approved browser section adds unregistered origin/tenant/metadata/request-size/quota protections and private projections over the model. Nine HTTP/browser/database checks include real second-origin forgery refusal and desktop/mobile consent persistence; 53 new unit tests, 1384 backend total. This does not implement production BFF/TLS/proxy/key/logging infrastructure or a distributed limiter. Read APP013_CUSTOMER_BROWSER_TRANSPORT.md.

- Latest continuation (owner: "continue", 2026-09-09) adds legacy-path isolation and unregistered CustomerConsentCaptureService. Explicit normalized address plus a valid customer credential; exact tenant/session/customer/conversation/marker recheck, one encrypted capture and privacy-safe audit in a bounded transaction. Identical replay never rewrites ciphertext/audit; replacement and malformed stored capture refuse. Expiry after persistence rolls back. No consent, verification or sending derives from capture.
- Server-owned marker is written only on fresh bootstrap, never caller-selected historical scope. Shared lock projects session/marker/capture only, not transcripts or entire conversation JSON. Captured address is kept private, returned only by the separately authenticated prompt; capture receipts contain status/deliveryAuthorized:false only.

- Existing WebchatIntegrationGuard establishes business-integration identity only. TriageDto.sessionId is caller supplied; neither can substitute for a customer credential. Appointment-management tokens have a different purpose and are not accepted.
- Unregistered CustomerConsentResponseService.start requires verified webchat_integration context with no impersonation. It always creates a new random session/conversation/placeholder customer transactionally. It accepts no existing-session identifier to adopt. A failure rolls back creation; a lost bootstrap response has no recovery/adoption path in this model.
- CustomerConsentCredentials uses a dedicated injected 32-byte signing key, strict key ID, HMAC-SHA-256 with signmons.customer-consent.v1 domain separation and fixed purpose claims. There is no environment reader, live key generator, DI registration, default key or fallback to existing encryption/integration/appointment keys.
- Session claims bind version/purpose, tenant, conversation, server-generated session, random token identity, issue time and expiry. Local model lifetime is 15 minutes, non-sliding. Prompt lifetime is at most 5 minutes, capped by original session expiry. Exact expiry refuses; future issuance, excessive lifetime, malformed/extra claims, wrong key/purpose/signature and cross-session combinations refuse. These are local implementation defaults for review, not deployed policy.
- A prompt token additionally binds the session-token identity, SHA-256 digest of randomized captured ciphertext, exact approved prompt digest, and expected initial evidence revision. It contains no address. Changing or re-encrypting the captured mailbox invalidates the prompt; the digest is not a consent fingerprint or mailbox verification proof.
- Prompt text is the D1-D4-approved wording. GRANTED requires an explicit separate mailboxConfirmed:true plus the distinct grant choice. DECLINED does not require address confirmation. No free-text yes, missing field, string boolean or caller authority override is accepted.
- Prompt/respond validate current active tenant, undeleted WEBCHAT conversation and scoped customer, exact session and canonical retained mailbox under transaction locks. The response creates the structured CUSTOMER receipt and immutable evidence atomically. Prompt expiry is checked again after persistence; failure rolls back. Concurrent identical submissions share one receipt; altered response/another outstanding prompt cannot create a second initial decision.
- A completed evidence history suppresses another prompt. Repeated response is a historical receipt only, never present-day permission or a send credential. Revocation, deliberate preference reopening/regrant and expired-session recovery are separate unfinished flows.
- Fresh service instances can verify an unexpired credential using the same keyring and return the same durable receipt. No durable cookie store, per-session logout/revocation list, renewal or recovery implementation is supplied. Conversation deletion and signing-key retirement refuse further use.

## Key lifecycle and transport review before live use

1. Supply a dedicated session/prompt signing key through reviewed secret storage and server-only loading. Never reuse conversation encryption, appointment management, integration or mailbox-fingerprint keys. Current code consumes injected bytes only; no live secret was generated, fetched or configured.
2. The model accepts at most two key versions. Signing uses the active version; verification may accept an explicitly retained previous version. Normal rotation can allow existing credentials to expire before removing the old key. Removing a key immediately refuses its tokens, including session-bound prompts signed under a newer key. A compromise requires immediate retirement, not a permissive fallback. Live rotation/distribution and incident operations remain unimplemented.
3. Mailbox fingerprints need a separately reviewed dedicated keyed adapter, tenant/purpose-separated serialization and versioned rotation policy. Do not recompute historical immutable evidence or silently treat different versions as equal. The existing fingerprint port still has no production implementation. Its test HMAC key and serialization are fictional proof, not deployable configuration.
4. Deliver bootstrap credentials only to the initiating browser over HTTPS through a reviewed server-side integration boundary. Never put the business integration key in the public/static client. A session token proves possession of this new session, not civil identity or control of the mailbox.
5. Resolve same-origin/allowlist, CSRF, rate limiting, abuse protection, response cache/referrer headers and redaction across HTTP/access/error/analytics logs before exposing a route. The local fixture uses memory-only browser tokens and private/no-store responses; it is not production cookie/BFF/CSRF acceptance.
6. Fresh protected sessions now carry server-owned customerSessionVersion:1. Legacy ConversationsService.ensureConversation and email observe/requestOnce refuse every present marker; both triage controller paths are tested to stop before downstream effects. Customer capture/prompt/respond require exact marker 1 under shared advisory/row locks. Never upgrade/adopt historical unmarked sessions. This JSON marker is application-owned, not database-immutable; privileged SQL/old-writer rollout and retention/deletion compatibility remain review obligations. Unmarked legacy flows retain existing behavior; complete credential-bound AI intake is still unfinished.
7. Local expiry/loss rule: no renewal or unauthenticated recovery/adoption. Clear private form/token on unavailable session; explicitly start a fresh scope, with office help for an existing appointment. A lost capture acknowledgment may retry identical input only with the same unexpired credential; expiry after capture/audit insertion rolls back. Browser reload loses memory-only credentials. Fictional desktop/mobile proof covers this rule, not production recovery, safe customer suppression/regrant, retention or hold compatibility. No token lifetime extension or historical event backfill.
8. D2 mailbox verification remains separate; no verification email or credential is issued here. D3 event expiry and D4 lifecycle enforcement remain unconnected to admission. New customer-session tokens are not appointment-management links, queue authority or permission to send.
