# APP-013 - Notification Center and Messaging Templates

## Ticket Summary

- Ticket ID: `APP-013`
- Repo: `signmons-calldesk-backend` (+ frontend app surface)
- Screen IDs: `SCR-APP-021`, `SCR-APP-022`, `SCR-TECH-005`
- Objective: centralize owner/dispatcher/technician/customer communication signals and template controls.

## In Scope

- Notification center for owner/dispatcher and technician events.
- Messaging template management for customer communications.
- Event categories:
  - intake created
  - urgency escalation
  - assignment update
  - payment status update
  - schedule confirmation/update
- Transactional appointment email after the calendar booking is committed:
  - ask for and retain the customer email once without repeating captured questions
  - confirmed date and Eastern Time arrival window
  - appointment reference and concise service type
  - private, absolute customer-management link
  - add-to-calendar attachment or standards-compliant calendar action
  - call/text fallback and private-link warning
- One updated customer email after a successful reschedule and one cancellation email after a successful cancellation.
- Delivery failure must not roll back a confirmed appointment; it creates an operator-visible failure with a safe retry path.
- Customer management credentials must not be copied into analytics, normal application logs or message-preview telemetry.
- Delivery status visibility (sent/failed/retry).

## Out of Scope

- External marketing campaign automation suite.
- Multi-channel social messaging orchestration.
- Advanced A/B experimentation framework.

## Acceptance Criteria (must all pass)

- [ ] Notification center displays role-appropriate operational events.
- [ ] Templates can be managed per tenant policy.
- [ ] Delivery status and failures are visible.
- [ ] A committed eligible appointment sends exactly one branded customer confirmation email with the confirmed window, reference, private management action and calendar action.
- [ ] Reschedule sends exactly one updated confirmation; cancellation sends exactly one cancellation notice without an active management action.
- [ ] Customer email is requested once, retained in the conversation/job record and never repeatedly requested after capture.
- [ ] Customer email-delivery failure does not undo the job or calendar event and is visible to operations for retry.
- [ ] Secure management credentials are absent from analytics, ordinary logs and operator message previews.
- [ ] Sensitive data is redacted per role boundaries.
- [ ] Notification events are auditable.

## Test and Evidence Plan

- Backend gates: `npm run -s build`, `npm test -- --runInBand`, `npm run -s arch:check`
- Frontend gates (if touched): `npm run -s build`, `npm run -s lint`, `npm test -- --runInBand`
- Evidence:
  - notification center screenshots
  - template configuration proof
  - failed-delivery handling proof

## Risks

- Template drift from policy/compliance constraints.
- Alert fatigue for dispatch roles.
- Overexposure of customer data in message previews.
- Forwarded appointment-management links acting as bearer credentials; copy must warn customers to keep the link private and destructive actions may require an additional verification policy.
