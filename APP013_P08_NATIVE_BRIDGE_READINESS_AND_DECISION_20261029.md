## Proposed smallest native bridge, still disabled until a later exact operation

1. **One authority chain.** Source-lock the existing role/restoration/Stage A/key/auth modules and the actual provider adapters. Bind one preselected operation ID, immutable approval document/commit/hash, project, exact tenant/job, disabled account ownership, fixed runtime identity, two role IDs, service/key ID, expected image and *dynamic* environment digest, windows, no-retry, retention, and allowance. Reject inconsistent cross-module approvals before credential access. Do not manufacture a new authority from the packet's fake plan.
2. **Real transport and output contracts.** Reuse the restoration CLI/SQL and Stage A HTTPS boundaries. Implement only the missing API Keys native descriptors and response parsers: Service Usage state/enable operation, exact key GET typed NOT_FOUND versus denial, create/delete long-running operations, metadata including `deleteTime`, and in-memory keyString. Validate omitted/null provider fields and safe fixed error categories using actual serialized boundary tests. No raw policy, bearer, key string, token, password or private account row in public evidence.
3. **Ownership and sequencing.** Fresh exact preflight; refuse foreign binding/key/account/traffic or a changed source/config pin. Attach the two existing time-conditioned roles only when absent and exactly qualified; read back their conditions. Require all four Stage A `CAN_ACCESS`; otherwise remove only owned bindings and stop before API Keys. Conditionally enable API Keys under an explicit owner retention decision; verify operation completion and service state; require typed absent key ID; create one restricted key; verify exact UID/etag/displayName/restriction ownership and obtain keyString privately. The packet must not assume the old `deleted` field or bypass LRO settlement.
4. **Resolve the key-hash authority gap before coding the live path.** Recommended: a single preapproved *derivation rule* that allows the new key's SHA256 to be bound from its exact owned creation/readback receipt into the auth plan inside the same process, without logging the string or accepting another key. The auth authority must verify the operation ID, resource, UID/etag, restriction and short-lived in-memory hash provenance. This changes the existing auth approval contract and needs explicit owner approval and local tests. It must not silently replace the current `exchange.keySha256` gate.
5. **Authentication and retirement.** Reuse the native auth controller for exact disabled test account → signBlob → Identity Toolkit exchange → same-job authenticated read → disable/revoke/session readback. Keep the key alive only through that flow. Then delete/read back that owned key, remove owned IAM bindings, retire temporary runtime/database/secret resources and read back normal traffic, sessions and private-plan absence. Never infer cleanup from IAM condition expiry or key delete response alone. A lost create/delete/grant response is UNKNOWN; read back exact ownership without automatic mutation retry. Report independent residuals and provide one separately bound closeout-only path.
