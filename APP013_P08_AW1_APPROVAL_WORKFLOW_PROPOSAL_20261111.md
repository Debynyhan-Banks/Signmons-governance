## Demonstrated problem and recommendation

R25 qualification timed out waiting for a password after a scheduled start; no qualification provider reservations. R26 recovery/hidden endpoint succeeded, but the chat approval was never given before qualification cutoff; inputs were correctly purged. Deployment/adoption/retirement remain complete. Repeating another timed recovery packet with the same handoff pattern does not fix this interaction problem.

Current connected_launcher.py publishes a ready marker then packet.wait_committed_decision polls Git; user must leave Terminal, send the exact stage approval in chat, wait for an assistant commit, then notice a hidden password prompt. Existing tests prove exact Git scope matching but do not provide a visible local approval-to-password handoff. The proposed change keeps exact scope and committed authority, and moves the owner's stage confirmation into that same attended Terminal window.

Recommend one session-opening chat approval of a concrete recovery packet, plus two explicit Terminal confirmations for the dynamically bound qualification and native operation. Those are still two separate exact approvals, not advance blanket approval. The assistant supervises the active session, verifies each sanitized confirmation against the published review/source/clock/authority, and commits the existing exact decision. The launcher never commits Git or creates provider authority itself. The current validators remain the execution gate.

Alternative A: keep chat approvals but add reminders; fewer code changes, still requires switching windows and is what failed R26. Alternative B: blanket conditional approval/automatically approve stages; rejected because amounts/scopes and current readiness are not known at initial approval. Alternative C: extend private retention/retry automatically; excluded. Recommendation changes the confirmation channel only, not resource scope, custody ceiling or required evidence.

## Proposed owner decision and delegation boundary

Approve local implementation of AW1 only. Each future live session must separately include explicit owner consent that their typed Terminal confirmations for that named session count as instructions to the assistant to record the displayed exact approval in Git. Local implementation approval alone does not enable that delegation or approve any future operation. Without that session consent, the existing chat approval path remains available and no Terminal file is treated as authority.

A Terminal confirmation is a local attestation, not cryptographic proof of the person's identity and not a substitute for existing owner-account checks. It must never be accepted from arbitrary tool output, an old marker, an unrelated file, or a bare “complete”/“yes”. Only the explicitly delegated session's fresh source-bound capture path qualifies. The assistant must not synthesize the owner's input. Unexpected files or ambiguous confirmation stop safely.

## Concrete user flow

1. Before opening Terminal, show one concise session summary in chat: purpose, earliest immediate start, hard stop/purge times, recovery actions, downstream approvals, exact spending boundaries and mandatory cleanup. Obtain one exact recovery/session approval and Terminal-confirmation consent. Source/readiness checks complete first. No scheduled gap between approval and first prompt.
2. Existing recovery asks for hidden SQL password. Existing source-locked handoff and Destination ID prompt follow. Never print secrets or private UUID/project inputs.
3. Terminal displays QUALIFICATION REVIEW: operation short ID and full scope/cleanup hashes, source SHA, max27CLI/20HTTPS/4SQL/1cache, read-only/no payment, absolute input/read/cleanup/purge deadlines. Ask owner to type a fresh exact phrase `APPROVE QUALIFICATION <operation-short-id> <nonce>` or `CANCEL`. No default, no Enter-to-approve. Wrong text does not confirm; cancellation/timeout triggers existing cleanup and purge. The nonce is local freshness context, not an authentication claim.
4. After confirmation, show “Approval recorded locally; waiting for verification. Next prompt: hidden SQL password.” Publish only a sanitized confirmation record bound to the full exact proposed decision and review hash. Assistant verifies it and commits the existing exact qualification decision; no new chat reply needed while the assistant actively supervises. Existing wait_committed_decision still refuses wrong/uncommitted/stale decisions. Password prompt follows in that same window; user remains there.
5. After successful qualification, Terminal displays NATIVE REVIEW: exact candidate/source, Sandbox/test mode, current amount/currency and same-job purpose (no raw private identifiers in retained public record), finite action inventory including temporary IAM/role/tag/key/webhook changes, actual cost/allowance limitations, cleanup and purge deadlines, and full exact scope hash. Owner types `APPROVE SANDBOX <operation-short-id> <nonce>` or `CANCEL`. Same independent assistant verification/commit path. No payment/runtime mutation before that exact committed decision. Existing Sandbox Checkout UI and operator bridge remain unchanged.
6. Cleanup already included in each exact scope runs unconditionally; no new approval prompt for mandatory cleanup. Terminal clearly distinguishes SUCCESS, SAFE STOP, CLEANUP UNCONFIRMED and PRIVATE PURGE VERIFIED using existing authoritative receipts. Assistant reports final outcome and checks process/private-file closure. No automatic next operation or retry.
