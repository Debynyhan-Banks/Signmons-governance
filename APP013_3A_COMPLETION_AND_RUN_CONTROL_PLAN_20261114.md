## Operating rules to adopt now

1. **Preparation happens before owner attendance.** Finish source review, local tests, proposed later-stage reviews and cleanup instructions first. Request sign-in only after its concrete packet and the dependent workflow preparation are ready and the owner confirms availability. After sign-in, require observed credential coverage for work, review/input time and the unchanged cleanup/purge reserve before launching recovery, qualification or native work. Foreground the owned standalone Terminal and confirm owner readiness before each timed hidden-input stage. Do not consume the cleanup reserve to finish work or extend fixed retention silently.
2. **Consolidate review, preserve authority.** Present one readable session overview showing purpose, expected owner actions, decision gates, limits, stop conditions and finish. Do not re-ask for routine work already authorized. Existing dynamically bound qualification/native decisions remain separate where required. Combining those decisions, changing timeouts, storing/reusing credentials, increasing retries or altering retention requires a specific proposal and owner decision first.
3. **Every attempt must answer a named question.** Before launch, record the previous stop, what changed or what new evidence the operation will obtain, the expected result and the cleanup owner. A new operation ID, renewed credentials or another “proceed” is not evidence that the failure is resolved. Passing local tests is not live readiness.
4. **One failed attempt ends the live session after cleanup.** Stay on the failing boundary. Report only: failed stage/code; confirmed cause versus UNKNOWN; cleanup status; smallest evidence or correction needed next. Do not roll immediately into a new full run. A repeated non-informative result triggers engineering/cloud-custodian review of the approach rather than another scheduled attempt. No provider/customer/support message is sent without authorization.
5. **Retain useful safe evidence.** Reuse existing stage/error/count/hash receipts. Check error propagation through the actual process boundary before live use. Preserve private-value restrictions and purge deadlines. Any added diagnostic field or retention change must be scoped before implementation; never retain raw passwords, tokens or provider payloads to make debugging easier.
6. **Keep reporting short.** Maintain one current remaining-work list with the blocker, responsible owner, last decisive result and next observable result. Canonical pointers should link to this plan and the latest evidence, rather than repeat the whole history. Keep historical receipts immutable. Run required checks and newly affected tests; do not rerun unrelated successful runtime suites merely to produce activity.

These are operational rules, not claims of new automated enforcement. Existing code continues to enforce only its inspected current checks. No new blocking checker has been implemented by writing this plan.
